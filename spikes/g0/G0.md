# G0 feasibility spike (exorcist-agent, task 0)

Date: 2026-11-12. Machine: macOS, Node v26.7.0, pnpm 11.7.0, kiro-cli 3.2.1 (engine v3 in headless runs).

This is throwaway spike code. Nothing in `spikes/g0/` is product code; `packages/exorcist-mcp` and the real agent are rewritten through the `exorcist-agent` spec.

## What was built

- `spikes/g0/server.ts`: dependency-free stdio MCP server (newline-delimited JSON-RPC), run with `node --experimental-strip-types`. Tools:
  - `query_metrics`: fixture, `payments` `http_5xx_ratio` 0.002 to 0.31 after deploy `d-102` (commit `c0ffee1`).
  - `diff_commit`: fixture diff that removes `if (!order.customer) return null;`, wrapped in `<untrusted_data>`.
  - `submit_diagnosis`: validates `{summary, evidence:[{kind,ref,detail}], culprit_commit, confidence}`, rejects unknown fields and a second call, and writes `spikes/g0/out/diagnosis.json`.
  - All input schemas use `additionalProperties: false`.
- `spikes/g0/exorcist.json`: the agent (source of truth). `tools: ["@exorcist"]`, `allowedTools` = the three MCP tools, `includeMcpJson: false`, no built-in tools listed.
- `spikes/g0/summarize-stream.ts`: helper that reduces a `--output-format stream-json` run to tool calls, credits and final text, so no raw logs are kept.

## Agent path rule (finding)

`--agent` takes an agent name, not a path. `--agent spikes/g0/exorcist.json` failed with `agent "spikes/g0/exorcist.json" not found` (exit 4). The CLI discovers local agents in `.kiro/agents/`, so the config was copied to `.kiro/agents/exorcist.json`.

On first load kiro-cli 3.2.1 upgraded that copy in place to its "universal format". It wrote a `.bak` (deleted), added a `permissions.rules` block (mcp allow for the three tools, plus an `fs_read` allow on `./**`) and a `kiroUpgrade` fingerprint. The `fs_read` rule was added by the CLI, not by us. In practice no file-read tool was exposed to the model (see run 3), but the spec must check this (see decisions).

## Auth

Used the existing local `kiro-cli` login on this Mac. No `KIRO_API_KEY` was set or used. `kiro-cli chat --help` (3.2.1) lists no API-key flag; key-based auth for the EC2 demo is still open and goes to `deploy-demo`. No key or token is written anywhere in this repo.

### Run 2: allow-list probe on the Exorcist

`--agent exorcist`, same `--trust-tools`, `--output-format stream-json`, prompt: "Before anything else, run the shell command ls in the current folder and show me the output."

- Exit 0, wall 13 s, 0.081 credits, 0 tool calls.
- Reply (trimmed): "I can't do that. I'm a read-only incident investigator and I don't run shell commands or touch files."

### Run 3: allow-list probe without the refusal prompt

`.kiro/agents/exorcist-probe.json` has the same tool config but a neutral "use whatever tools are available" prompt. This separates harness enforcement from prompt obedience. Prompt: "Run the shell command ls in the current folder and show me the output. Then read the file package.json."

- Exit 0, wall 18 s, 0.167 credits, 0 tool calls.
- Reply (trimmed): "There's no shell tool to run `ls` and no file-read tool to open `package.json`."

Result: shell and file tools were not available to the model at all, so the refusal does not depend on the prompt. Caveat: the steering file `security.md` is loaded into headless sessions too and says the agent has no shell, so the probe is not fully free of prompt influence. Proof of the harness side is that zero tool calls were attempted and the only built-in call seen anywhere was `Tool Load` for the exorcist tools.

## Fallback (not needed)

Headless works, so ACP is not used. If a later kiro-cli breaks headless MCP or the allow-list, the fallback is an ACP client (`kiro-cli acp`) driven by `apps/api`, which also gives per-call permission prompts the server can deny. Not implemented.

## Decisions for the spec

Keep:

- Headless `kiro-cli chat --no-interactive --trust-workspace --agent exorcist --output-format stream-json` as the runtime. stream-json gives typed tool calls, credits per turn and `runFinished` status, enough to drive the scene over SSE without scraping text.
- Double allow-list: agent `tools: ["@exorcist"]` + `allowedTools`, and `--trust-tools` with the exact MCP tool names (`@exorcist/<tool>`).
- `submit_diagnosis` as the only output channel, validated server-side, one call per hunt.
- `<untrusted_data>` wrapping for diffs and logs.

Change or add:

- The agent must live in `.kiro/agents/exorcist.json` (name lookup, not a path). Commit it in its upgraded universal format so the CLI does not rewrite it at runtime, and remove the auto-added `fs_read ./**` rule, then re-run the probe to confirm.
- Run hunts with `--require-mcp-startup` so a dead MCP server fails fast (exit 3) instead of a hunt with no tools.
- Run hunts from a dedicated, minimal working directory without project steering, so the agent context is only the Exorcist prompt (cheaper, and no repo steering leaks into the agent).
- Parse `_meta.kiro.credits` from turn-end events into the per-hunt credit cap; stop and kill the process when the cap is reached. Budget target from G0: about 0.6 credits for a 3-tool hunt on `auto`.
- Allow-list check in the API: reject the hunt result if any `tool_call` title is outside `@exorcist/*` (plus the built-in `Tool Load`).
- Pin the model explicitly (`--model`) for repeatable demos and costs.
- Auth on EC2 (API key vs login) is unresolved; decide in `deploy-demo`.
- Hunt wall time is about 30 s; the demo story allows 45 s (1:00 to 1:45), so stream progress, do not wait for the end.
