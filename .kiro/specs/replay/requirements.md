# Requirements Document
## Introduction
`replay` is the ninth product spec of Haunted Ops, after `foundation`, `haunted-lab`, `ingest-haunt-score`, `scene-engine`, `exorcist-agent`, `fix-proposal-flow`, `accessible-mode` and `deploy-demo`. A replay is a recorded real incident of the lab (services going bad, the hunt with its steps, evidence and diagnosis, the fix proposal with its checks, the pull request, the merge and the deploy), turned into one sanitized JSON file that a person has read and approved. The file is committed under `fixtures/replays/<id>.json`, seeded into PostgreSQL, served read-only by the API and played back in the web app at `/replays/<id>`, in the scene and in Accessible mode. The steering rule "replays use sanitized fixtures reviewed by a human" is the reason for the whole design.
The spec also closes two flaky tests of earlier specs (a property test of the pull request text, and fixed sleeps in the hunt tests), which turned out to hide a quadratic regular expression in the text sanitizer, and fixes three findings of the `deploy-demo` review.
It starts no cloud resource, opens no connection to a server, to GitHub or to the real `kiro-cli`, and spends no credits. The real replay files are made later by the orchestrator, on real data, with the tools this spec delivers.
## Glossary
- **Workspace**, **API**, **Web**, **Lab**, **Hunt**, **Proposal**, **Scene**, **Accessible mode**, **Demo server**: as defined in the earlier specs.
- **Replay**: the feature, one recorded incident played back. The word is used for nothing else; the fake `kiro-cli` has a mode with a similar name that this spec does not touch and shares no code or name with.
- **Replay file**: the JSON file `fixtures/replays/<id>.json` of type `ReplayFile`.
- **Frame**: one item of `frames`: a time `t` in milliseconds and the parts of the state that change then. Each part a frame names REPLACES that part (`services` the whole list of four, `hunt` a full Hunt detail or `null`, `proposal` a full Proposal view or `null`).
- **Review**: the block `{ reviewedOn, by, note, sha256 }` that a person writes with the review tool after reading every string of the file. `sha256` is the hash of the content the person read (the file with `review` set to `null`, as canonical JSON). A file with `review: null` is unreviewed.
- **Sanitizer rules**: the scrubber of `tools/sanitize-replay/sanitize-hunt-stream.mjs` and the rules of `sanitizePrText`, which the Builder applies, and the forbidden string kinds that the validator checks again.
- **Builder**: `tools/replay-build/build-replay.mjs`, which reads one incident from a database and writes a Replay file with `review: null`.
- **Review tool**: `tools/replay-build/review-replay.mjs`, which prints a plain-text reading of a file and, only with `--approve`, writes the Review.
- **Replay store**: the `Replay` table of PostgreSQL and `seedReplays`, which fills it from a folder.
- **Player**: the code in `apps/web/src/replay/` that loads a file and plays its frames; the **frame player** is its pure part (`player.ts`).
- **Synthetic replay**: `apps/api/test/fixtures/replays/synthetic-error-spike.json`, made by the Builder from rows that a test inserts, marked as synthetic in its title, used by tests only.
## Requirements
### Requirement 1: The Replay file
**User Story:** As the developer, I want one strict, small file format shared by the tools, the API and the Web, so that a replay that passes the validator is safe to store, serve and play.
#### Acceptance Criteria
1. THE `ReplayFile` type and `validateReplayFile` (built with `makeValidator`) SHALL be in `packages/shared/src/replays.ts` and SHALL reuse `ServiceState`, `HuntDetail` with `checkHuntDetail` and `ProposalView` with `checkProposalView`.
2. THE validator SHALL accept only: `version` 1; `id` matching `^[a-z0-9][a-z0-9-]{2,47}$`; a `title` of 1 to 80 characters on one line; a `scenario` of `error-spike`, `fog` or `dark-room`; `recordedOn` as a real date `YYYY-MM-DD` with no time; `durationMs` an integer from 1 to 900000; `review` `null` or `{ reviewedOn, by, note, sha256 }` with a date, 2 to 4 letters, at most 200 characters and the hash of the file (criterion 7.8); and 1 to 400 frames.
3. THE validator SHALL require `t` of each frame to be an integer, `0` for the first frame, not decreasing, and not above `durationMs`, and SHALL require `services` in the first frame, always the four services in room order.
4. THE validator SHALL refuse an unknown key at any level it checks, a `prUrl` that is not `https://github.com/Akar-Samudra-Artifisial/Haunted-Lab/pull/<n>`, and a file above 256 KiB as UTF-8 JSON.
5. THE validator SHALL refuse any string that holds an email address, a home or temporary path, a token shape (a known prefix or an unbroken run of 32 or more characters that is not a 40-hex commit SHA), a UUID, an account id, an IP address other than 127.0.0.1, a host name, an ANSI or control character other than the line feed, or is longer than 1000 characters, and SHALL name the path of the string, never its text.
6. THE validator SHALL be total: any input gives a result and nothing is thrown.
7. THE shared package SHALL also export `validateReplayList` (the answer of `GET /api/replays`), `replayListItem` and `applyReplayFrame` (the fold of one frame into a state).
### Requirement 2: Building and reviewing a replay
**User Story:** As the orchestrator, I want a tool that turns a recorded incident into a sanitized file and a tool that makes a person read it before it is approved, so that no real data reaches the demo by accident.
#### Acceptance Criteria
1. THE Builder SHALL read ONE incident, with `find*` calls only, from the database given by the environment variable `DATABASE_URL` (never an argument), and SHALL never print the URL or any database message.
2. THE Builder SHALL write `fixtures/replays/<id>.json` (or `--out-dir`) with `review: null`, SHALL refuse to replace an existing file, and SHALL take the window from the Signal rows (60 seconds before the incident opened to 30 seconds after the last event, both settable), at most 15 minutes.
3. THE Builder SHALL make one `services` frame for each second in which a poll changed something (the haunt level by the same hysteresis as the ingest), SHALL merge the polls of one second, SHALL turn the Hunt steps and the Proposal status changes into frames at their stored times, and SHALL keep at most 400 frames and 256 KiB by dropping services-only frames evenly.
4. THE Builder SHALL pass every string through the scrubber of `tools/sanitize-replay/sanitize-hunt-stream.mjs` (exported, not copied) and `sanitizePrText`, SHALL rewrite ids to stable fake ids derived from the replay id, SHALL set the pull request link to the lab repository, SHALL replace the login of who merged by `reviewer`, SHALL move all times to the recording date at midnight, and SHALL never write `aiFailDetail`, raw stream lines, work folder paths or the credits of a single tool call.
5. IF the built file fails `validateReplayFile`, THEN THE Builder SHALL stop with the field paths and never a value, and exit 1 (2 for a usage error).
6. THE Review tool SHALL print every string of the file with its path, frame by frame, and SHALL write the Review only with `--approve`, after checking the file and the block again.
7. THE folder `fixtures/replays/` SHALL hold a `README.md` that says how to build, review and add a replay, and no replay file in this spec; the Synthetic replay SHALL be the only replay file, and SHALL be made by the Builder from rows that the integration test inserts into the test database.
### Requirement 3: Store and API
**User Story:** As the demo server, I want replays in PostgreSQL and a read-only API for them, so that the single store holds state, events and replays and the internet can only read.
#### Acceptance Criteria
1. THE schema SHALL have a model `Replay` (`id`, `title`, `scenario`, `recordedOn` as a date, `durationMs`, `body` as JSON, `sha256`, `createdAt`, `updatedAt`) with one migration, and `db:drift` SHALL report no difference.
2. THE function `seedReplays(prisma, folder)` SHALL read and validate every `*.json` file before it writes, SHALL stop on an invalid file (and on a file whose name is not `<id>.json`) naming the file and the paths with nothing written, SHALL skip a file with `review: null` and name it, SHALL keep a row whose `sha256` is the hash of its file and whose body has that hash, and SHALL delete a row that has no reviewed file.
3. THE script `deploy/server/seed.mjs` SHALL call it with the release's `fixtures/replays/`; `pnpm --filter @haunted-ops/api seed:replays` SHALL do the same locally.
4. THE script `deploy/build-release.sh` SHALL copy `fixtures/replays/*.json` and the release check SHALL refuse a replay file without a review (`replay_unreviewed`).
5. THE `ReplaysModule` SHALL answer `GET /api/replays` (id, title, scenario, recordedOn, durationMs, newest first) and `GET /api/replays/:id`, SHALL answer 404 for an id that breaks the pattern or is not stored, and SHALL add no route that writes.
6. THE API SHALL validate the stored body again before it sends it, SHALL answer 500 with no content for a row that is invalid, unreviewed or whose id or duration differs from its columns, and SHALL log the id only.
7. THE two answers SHALL carry `Cache-Control: public, max-age=300`; an error SHALL NOT.
### Requirement 4: Playback in the Web
**User Story:** As a judge, I want to open a recorded incident and watch it in the house or read it in the table, with controls I can use by keyboard, so that I see the whole story without waiting for a live incident.
#### Acceptance Criteria
1. THE Web SHALL parse `/replays` (the list) and `/replays/<id>` (the player) next to `huntIdFromPath`, and SHALL load everything specific to replays with `import()` on those routes only; the entry chunk SHALL grow by at most 0.5 KiB gzip and SHALL NOT reach the replay chunk with a static import.
2. THE bundle check SHALL have a budget for the replay chunk (measured + 20 percent, at most 16 KiB gzip) and SHALL fail when the entry reaches that chunk statically.
3. WHILE a replay is shown, the frames SHALL be the single source of `services`, of the Hunt detail and of the Proposal that the Scene mount, the table, the detail panel and the announcer read; THE Web SHALL open no event stream and make no live request, and SHALL not fetch the Hunt detail from the API.
4. THE player SHALL have, keyboard reachable and labelled: Play (with `aria-pressed`), speeds 1×, 2× and 4×, previous and next frame, a range input for the position with `aria-valuetext` such as "1 min 20 s of 3 min", and a link "Back to live".
5. THE page SHALL show "Replay of <date>, not live" in the header and at the start of the table caption, and SHALL start paused when the browser asks for reduced motion or Accessible mode is on, and playing otherwise.
6. THE announcements SHALL go through the one existing live region, and a jump with the range input or by several frames SHALL announce the state reached once.
7. FOR every position of a replay, the table SHALL say every fact the Scene shows (level, reason, dark or lit, incident, hunt, fix).
8. IF the replay does not exist, THEN THE page SHALL say "This replay does not exist" with a link to `/replays`; IF the API is down or sends an invalid or unreviewed file, THEN THE page SHALL show a plain message and SHALL NOT crash, also in a `?demo=1` build with no API.
9. THE README SHALL have one line for `/replays` under the live demo line.
### Requirement 5: Flaky tests
**User Story:** As the developer, I want the suite to pass under load for the right reason, so that a failure means a defect.
#### Acceptance Criteria
1. THE workspaces that use fast-check SHALL load one vitest setup file that gives each test file one seed (`FC_SEED` or random), prints the seed with the `FC_SEED` and `FC_PATH` that replay a failure, and takes `FC_PATH` from the environment; `docs/DEV.md` SHALL say so. The `numRuns` of a property SHALL NOT be lowered to hide a failure.
2. THE time of `sanitizePrText` on adversarial input (long runs of `<`, `[`, `@`, `!`, backticks, `http` and nested brackets) SHALL be measured; any regular expression that takes more than linear time SHALL be replaced by a linear scan, and a 64 KiB adversarial input SHALL be sanitized in under 200 ms for every cap.
3. THE hunt tests SHALL wait for a process to be gone by polling up to a deadline, never by a fixed sleep, where they wait for a condition.
4. THE full `pnpm test` SHALL pass three times while a second `pnpm test` of the API runs.
### Requirement 6: Review findings of deploy-demo
**User Story:** As the operator, I want the three open findings of the deploy review closed, so that a key that systemd would misread is refused and the pre-flight reads the key as the guard does.
#### Acceptance Criteria
1. THE `kiro` profile of the env guard SHALL also refuse a `KIRO_API_KEY` that holds `\` or `"`.
2. THE `api` profile SHALL refuse `KIRO_API_KEY` (it belongs in `kiro.env` only), by name only.
3. THE pre-flight SHALL read the key with `scripts/read-env-value.mjs`, which uses the parser of the env guard (spaces around `=` and the value trimmed, then the quotes), and the release SHALL ship that script; a test with the line `KIRO_API_KEY = "<key>"` SHALL give the same value in both.
### Requirement 7: Review findings of replay
**User Story:** As the developer, I want the findings of the two reviews of this spec closed, so that two test runs never break each other, the validator refuses what a real incident can leak, and a reviewed file cannot change without a new review.
#### Acceptance Criteria
1. THE global setup of the API tests SHALL take a session-level advisory lock (`pg_try_advisory_lock` with a fixed key) on its own connection before it drops the `public` schema, SHALL keep it until teardown, and, when another run holds it, SHALL print once "another api test run is using the test database, waiting", poll every 2 seconds for up to 10 minutes and then fail with that message; a test with two connections SHALL show that a second setup does not work while the first holds the lock; `docs/DEV.md` SHALL say so.
2. EACH property test of `apps/web` and `packages/shared` that renders or runs more than 100 cases SHALL have an explicit timeout of 30 seconds as the third argument of `it`; no global timeout and no `numRuns` SHALL change.
3. THE fast-check setup of every workspace (`setup-fast-check.ts` for Vitest, `scripts/fast-check-setup.mjs` for `node --test`) SHALL print the seed only when a property failed (the error comes from `fc.assert`, its message holds "Property failed"), and SHALL stay silent for a plain assertion, a timeout or any other error; both cases SHALL be tested.
4. THE validator SHALL refuse any host name (`label.label...` whose last label is 2 to 24 letters, all lower or all upper case, and is not the ending of a file such as `yaml`; a last label that is a common host ending (`com`, `io`, `internal`, ...) counts in any case, and `py`, `md` and `sh` are a file only with one label before them), with `github.com` allowed only inside a valid lab `prUrl`; service names, tool names, lab file names, version numbers, decimals, timestamps and prose SHALL NOT be refused, and the accepted shapes SHALL be listed in a comment and tested.
5. THE validator SHALL refuse an IPv4 address only when each octet is 0 to 255 and the number is not preceded by a letter, a digit or a dot (so `v1.2.3.4` passes), SHALL refuse an IPv6 address (`::1`, compressed and full forms), the characters U+200B to U+200F, U+202A to U+202E, U+2066 to U+2069 and U+FEFF, an HTML tag (`<` followed by a letter, `/` or `!`), any `http://` or `https://` URL that is not the `prUrl` of the lab, and a `/root/` path.
6. EVERY check of the validator on a string SHALL take linear time: a 64 KiB adversarial text of any shape SHALL be checked by each rule in under 200 ms, and a file of such strings in under 200 ms; a property test SHALL show that each new forbidden kind put anywhere fails and that each allowed shape put anywhere passes.
7. THE Builder SHALL read the database URL from `DATABASE_URL` only (the option `--database-url` is gone, because an argument shows in `ps` and in the shell history), SHALL scrub again after `sanitizePrText` until nothing changes (removing an invisible character can join a token), SHALL replace host names, IPv6 addresses, mentions and `/root/` paths, SHALL remove zero-width characters, and SHALL stop with a clear message when `packages/shared/dist` or `apps/api/dist` is older than its sources.
8. THE review tool, with `--approve`, SHALL write `review.sha256`, the SHA-256 of the file with `review` set to `null`, as canonical JSON (keys sorted, no spaces: the same text from a file and from a `jsonb` column); THE validator SHALL refuse a review whose `sha256` is missing, malformed or not that hash, so that an edit after the review fails, and a new run of the review tool SHALL read the file again and write a new hash.
9. THE release check SHALL run the full validator on each `fixtures/replays/*.json`, SHALL require a review with `reviewedOn` and `by` as strings (`review: {}` is `replay_unreviewed`), SHALL name a file that does not validate, whose name is not `<id>.json` or that is larger than 1 MiB `replay_invalid`, and `deploy/build-release.sh` SHALL refuse a link or anything that is not a regular file in `fixtures/replays/`.
10. THE `sha256` of a `Replay` row SHALL be the hash of the canonical JSON of its file; THE seed SHALL refuse a file whose review hash does not match, and SHALL rewrite a row whose body does not have the hash of its row; THE list route SHALL leave out, and THE single route SHALL answer 500 for, a row that does not validate, is not reviewed, differs from its columns or whose `sha256` is not the hash of its body, logging the id only.
11. THE `kiro` profile of the env guard SHALL also refuse a single quote in `KIRO_API_KEY`; THE pre-flight SHALL read `LAB_READ_TOKEN` from `api.env` and `lab.env` with `scripts/read-env-value.mjs`, so that `LAB_READ_TOKEN = "x"` matches `LAB_READ_TOKEN=x` as the env guard sees them; both SHALL be tested.

### Requirement 8: Last validator gaps
**User Story:** As the developer, I want the last gaps found in the validator, the release and the seed closed, so that a public demo never shows a host, an address or an invisible character.
#### Acceptance Criteria
1. THE validator SHALL treat `py`, `md` and `sh` as a file ending only when ONE label comes before it (`app.py`, `README.md`, `run.sh`); with two or more labels (`staging.example.sh`, `db.prod.md`, `a.b.py`) the token SHALL be a host; a last label in any case whose lower case is one of `com net org io dev app co ai id me info biz cloud xyz tech site online sg us uk de jp internal local lan corp home` SHALL be a host ending (`Staging.Example.Com`), and a mixed-case last label outside that list (`Done.Next`) SHALL keep today's rule; the check SHALL stay one linear pass.
2. WHEN a hex-colon run starts with exactly one `:` (`addr:fe80::1`, `ip:2001:db8::7`), THE validator SHALL drop that `:` and check the rest without the left-boundary check; a run that starts with `::`, and `std::vector`, `12:30:45`, SHALL keep today's result; THE Builder SHALL mask the address through the same function (`addr:[ip]`).
3. THE validator SHALL also refuse U+061C, U+2028, U+2029, U+2060 to U+2064 and U+E0000 to U+E007F, and THE Builder SHALL remove the same full set.
4. `deploy/build-release.sh` SHALL refuse a build when `fixtures/replays` is itself a symbolic link, and THE seed SHALL count only regular files: a folder or a link named `*.json` SHALL stop it with the file name (`not_regular_file`), like an invalid file.
5. `pnpm test:scripts` SHALL print the fast-check seed of a falsified property (`scripts/fast-check-setup.mjs`); no code change is asked for the flaky test that failed once.

### Requirement 9: The IPv6 gap behind a word, and two flaky Web tests

**User Story:** As the developer, I want an address behind a label such as `device:fe80::1` refused too, and the two Web property tests that failed once under heavy load to stop failing, so that a public demo never shows an address and the checks are stable.

#### Acceptance Criteria

1. WHEN a hex-colon run starts inside a word (the character before it is a letter, a digit or `_`) and has a single `:`, THE validator SHALL also check the part after its first `:`, without the left-boundary check and with the right-boundary check kept, so that `device:fe80::1`, `id:fe80::1`, `ipv6:2001:db8::7` and `abcde:fe80::1` are refused (the Builder already masks them: its pattern starts after the `:`); `std::vector`, `12:30:45`, `time:12:30:45`, `device:12:30:45`, `ab12fe80::1`, `zx::1` and `a:b:c:d:e:f:1:2:3` SHALL stay accepted.
2. THE validator SHALL refuse `a::b` (and any compressed run of 1 to 7 hex groups that is not inside a word), because it is the valid address `a:0:0:0:0:0:0:b`; the design and the code agree on this, and a test names it. A 64 KiB text of any shape, the new ones included, SHALL still be read in under 200 ms.
3. THE Web tests "has levels that follow stepHaunt over the metrics it shows" (`demo.property.test.ts`) and "loads and mounts only while off, and destroys one renderer per mounted Scene" (`accessible-mode.test.tsx`) SHALL have a timeout of 30 s of their own, and the second SHALL poll each wait for up to 5 s instead of the 1 s default; `numRuns` SHALL not change.

### Requirement 10: The replay folder reaches the server

**User Story:** As the orchestrator, I want the release to always carry `fixtures/replays/`, so that the install seed does not stop on a missing folder before the first replay exists.

#### Acceptance Criteria

1. `deploy/build-release.sh` SHALL copy `fixtures/replays/README.md` into the stage (and stop when it is missing), so the tarball, which holds files only, always holds the folder.
2. THE seed SHALL keep its rule: a missing folder is an error, and a folder that holds only `README.md` seeds 0 replays and succeeds.
3. `scripts/release-check.mjs` SHALL refuse a release without `fixtures/replays/` with the finding `replay_folder_missing`.
4. A test SHALL show that the tarball of a tree with zero replay files lists `fixtures/replays/README.md`, and `docs/DEPLOY.md` SHALL say that the release always carries the folder.

### Requirement 11: Replay text, one clock and load-proof timing tests

**User Story:** As the person who reads a replay, I want code names left as written and one clock in the file, and as the developer I want the timing tests to hold on a busy machine, so that the first real replay reads true and the checks are stable.

#### Acceptance Criteria

1. THE validator SHALL keep one exported, frozen list `CODE_OBJECTS` (at least `Promise Array Object JSON Math Number String Boolean Date Map Set WeakMap Reflect Symbol BigInt Intl Error URL Buffer process console fs path os crypto http https util stream child_process res req ctx app router prisma this window document`), and SHALL NOT treat as a host name a token of exactly two labels whose first label is in that list (case-sensitive, exact) and whose second label matches `^[A-Za-z_$][A-Za-z0-9_$]*$` (`Promise.all`, `Array.from`, `Object.keys`, `fs.readFile`, `os.path`).
2. EVERY other host verdict SHALL stay: every accepted and refused example of `replays.hosts.test.ts` keeps its result, and `promise.all.example.com`, `Promise.all.com`, `console.kaktua.com`, `process.example.org`, `Promise.example.com` and `www.Promise.all` SHALL be refused.
3. THE Builder SHALL decide host names with the same `hasHostName` (no second copy of the rule), so that `(Promise.all)` stays as written in a built file.
4. THE Builder SHALL move the window start to 12:00:00 UTC of the recording date, and SHALL rewrite every clock time inside every string with the same shift as the timestamps (full ISO UTC `YYYY-MM-DDTHH:MM:SS(.sss)Z`, `HH:MM:SSZ`, `HH:MM:SS`, `HH:MM`, each in its own format; a bare clock read on the UTC date of the window start, on the day before or on the day after, whichever lands nearest the window; a bare date of the incident day or of the day before kept as written, because the recording date is the date of the window start); a duration (`1622ms`), a ratio (`3:2`) and part of a longer number SHALL NOT be touched.
5. WHEN a clock lands more than 7 hours from the window, THE Builder SHALL leave it as it is and stop with `clock_out_of_range` and the field path, never the value.
6. THE validator SHALL refuse a string that holds a full ISO UTC time whose date is not `recordedOn` (`foreign_date`, field path only), and SHALL NOT check a bare `HH:MM`.
7. THE adversarial test SHALL check growth, not wall-clock time (task 13, criterion 12.6, replaced the first method of this criterion, a median of 5 runs at 64 KiB over 8 KiB, which failed on a busy machine): a ceiling of 2 s per call and a test timeout of 60 s stay. Property 2b SHALL have a 60 s timeout, its time alone SHALL be measured and reported, and `numRuns` SHALL NOT be lowered without a reason.
8. WHEN a test that ran a property ends by timeout, THE Vitest fast-check setup SHALL print `[fast-check] timed out` with the seed; a falsified property SHALL keep its own line.
### Requirement 12: Host-like code members, epoch numbers, zone offsets and load-proof timing
**User Story:** As the person who reads a replay, I want no host name, no epoch number and no zone offset to pass as code or as prose, and as the developer I want the timing tests to pass on a busy machine, so that a real replay never leaks the hour of an incident and the checks are stable.
#### Acceptance Criteria
1. THE validator SHALL export one frozen set `HOST_LIKE_MEMBERS` of lower-case host endings (at least `com net org io dev app ai co cloud internal local localhost localdomain corp lan home intranet private test example site online tech me us uk id sg eu biz info xyz`), and SHALL treat a name of exactly two labels whose first label is in `CODE_OBJECTS` as code only WHEN its second label, compared in lower case, is an identifier AND is NOT in that set (this narrows criterion 11.1). `fs.internal`, `app.corp`, `res.dev`, `prisma.io`, `crypto.com`, `Date.com`, `console.IO` and `path.Local` SHALL be host names; `Promise.all`, `Array.from`, `Object.keys`, `fs.readFile`, `res.json`, `Date.now` and `JSON.parse` SHALL stay accepted. THE Builder uses the same `hasHostName`, so `(Promise.all)` stays as written and `app.corp` becomes `[host]`. The check SHALL stay linear.
2. THE Builder SHALL read an ISO date-time with `Z` or with an offset `+HH:MM` or `-HH:MM` as ONE instant, shift it with the shift of the timestamps and write it in `Z` form, and the alternative `HH:MM(:SS)` SHALL NOT start inside an offset or a longer number (no digit, `:`, `.`, `+` or `-` before it).
3. THE Builder SHALL shift by the same offset an epoch number of 10 digits in 1400000000 to 2100000000 (seconds) or of 13 digits in 1400000000000 to 2100000000000 (milliseconds), standing alone (no letter, digit, `_` or `.` before it, no letter, digit or `_` after it), whose instant is within one day of the incident window, and write it with the same number of digits; any other number of that shape SHALL stay as it is.
4. THE validator SHALL refuse a string that holds an epoch-shaped number of those ranges whose UTC date is not `recordedOn`, and a string that holds an ISO date-time with an offset other than `Z` or `+00:00`; the finding is the field path only, never the value.
5. THE Builder SHALL read a bare clock on the UTC date of the window start, on the day before or on the day after, whichever lands nearest the window, and SHALL keep a bare date of the incident day or of the day before as written (the recording date is the date of the window start, so the shift moves no bare date); THE requirements 11.4 and the design SHALL say so, as the code does.
6. EVERY timing test of linear time (the 128 KiB test of the validator, the 128 KiB tests of `sanitizePrText` and of `replaceMarkdownLinks`) SHALL measure growth and not wall-clock time: for each shape the minimum time per call at 128 KiB divided by the minimum time per call at 16 KiB SHALL be at most 20 (linear is about 8, quadratic about 64). Each sample SHALL repeat the call until at least 20 ms of wall time have passed and record the time per call as CPU time of the thread (`process.threadCpuUsage()`), the samples of the two sizes SHALL alternate, the minimum of 7 samples per size SHALL be used after one warm-up, there SHALL be no floor on the small time, a ceiling of 2 s per call SHALL guard against a hang, and each test SHALL have a 60 s timeout.
7.
